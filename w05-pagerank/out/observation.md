# Week 5 Observations · Link Analysis & PageRank

## Task 1 · PageRank, Dead Ends, and Spider Traps
- **Dead End Handling**: In the broken version without teleportation (`pagerank_no_teleport`), dead ends have no out-links, so their rank is dropped rather than propagated, draining total graph rank to near-zero ($0.0000$). In our fixed version, we redistribute each dead end's rank ($\beta \sum_{v \in \text{dead}} r[v]$) uniformly across all $n$ nodes, ensuring total rank is strictly conserved ($\sum r = 1.0$).
- **One Fix for Two Failures**: Adding uniform random teleportation makes the underlying Markov chain ergodic (both irreducible and aperiodic); every state is reachable from any other state in one step with probability $\ge (1 - \beta)/n$, preventing rank from permanently leaking out of dead ends or accumulating indefinitely in absorbing spider traps.
- **Physical Meaning of $\beta$**: $\beta$ represents the probability that a surfer follows an existing hyperlink on the current page. With probability $1 - \beta$, the surfer gets bored or reaches an impasse and teleports to an arbitrary page chosen uniformly at random.

## Task 2 · Convergence Behavior
- **Shape as $\beta \to 1$**: The required iteration count increases from 14 ($\beta=0.50$) to 24 ($\beta=0.99$). The error contraction per iteration is bounded by $|\lambda_2| \le \beta$. As $\beta \to 1$, the spectral gap $1 - \beta$ shrinks toward 0, slowing geometric error decay and requiring more iterations to reach the convergence tolerance.
- **Scaling (A4: Iterations vs. Wall Time)**: Iteration count is nearly invariant to graph size (20 $\to$ 21 iterations for $\beta=0.85$ between $N=1,200$ and $N=20,000$) because the spectral gap and mixing time depend on scale-free network expansion rather than $N$. Wall time grew by ~23×, scaling linearly with the number of edges $O(|E|)$ processed each iteration.
- **Ranking Stability (A6)**: The top 6 nodes remained completely stable across all tested betas, but boundary rankings shifted between $\beta=0.50$ and $\beta=0.70$ (where `p00004` overtook `p00000` for 7th place). This demonstrates that published PageRank rankings are sensitive to the chosen parameter $\beta = 0.85$ and should not be interpreted as absolute ground truth.

## Task 3 · Sparse Representation
- **Stored Data vs. Baseline**: Instead of the dense $n \times n$ matrix $M$ ($n^2 = 1,440,000$ floats), we retain the sparse adjacency list and hold only two float vectors of size $n$ (`r` and `nr`), requiring strictly **$2n = 2,400$ floats** (**600× memory reduction** and **88× speedup**). Edge weights are computed on the fly as $1/\text{deg}(u)$.
- **Teleport Term as a Non-Dense Operation (R5)**: The teleportation term $(1 - \beta)/n$ and the dead-end redistribution $\beta \cdot \text{dead\_sum} / n$ add the exact same constant scalar to every node. We compute this scalar once per iteration in $O(1)$ time (`base = (beta * dead_sum + (1 - beta)) / n`) and initialize `nr = [base] * n` in $O(n)$ time. Only actual edges $O(|E|)$ are traversed.
- **Difference from Dense Answer**: Worst-case per-node difference is **$1.17 \times 10^{-15}$** (well within $10^{-9}$). This microscopic discrepancy arises solely from floating-point accumulation order between dense row dot-products and sparse forward-push scatter operations.

## Task 4 · Large Scale & Spark Comparison (Optional)
- **Single-Process Limit & Bottleneck (A3)**: Single-process sparse PageRank operates efficiently at 50,000 nodes (1.88s, 20.4 MB peak) and 500,000 nodes (27.70s, 192.4 MB peak for 3.75M edges). However, past a few million nodes, storing Python tuples and adjacency lists in memory triggers severe memory pressure and swapping, making memory capacity the primary bottleneck that halts single-machine execution.
- **Spark Ratio at 50,000 Nodes (A5)**: At 50,000 nodes, Spark is significantly slower (~3×-5× slower) or fails if Java/PySpark is not installed (`ModuleNotFoundError`). The extra time is consumed by JVM initialization, Py4J socket IPC, dataset partitioning, RDD serialization (Pickle), and disk-backed shuffle staging.
- **Spark Rank Deficit (A7)**: The given `spark_pagerank` produces a rank sum less than 1 (e.g. 0.9959) because dead ends (nodes with no out-links) are omitted from `links.groupByKey()`. In `links.join(ranks)`, these dead-end nodes are dropped and their rank evaporates instead of being redistributed. Moreover, nodes with in-degree 0 produce no tuples in `contribs`, so `reduceByKey` drops them. To fix it, one must aggregate lost dead-end rank each iteration and broadcast it back.
- **Memory Curves (A6)**: Single-process memory grows linearly and monolithically in Python heap ($O(V + E)$). Spark memory per executor is bounded because partitions are processed in parallel streams and spilled to disk when memory thresholds are exceeded.
- **When to Use Spark**: Spark is the appropriate tool when the graph exceeds the physical RAM of a single workstation, requiring distributed partition storage across a cluster with automated node-failure recovery.
